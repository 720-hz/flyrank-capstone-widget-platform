# Build log

Honest AI-usage log, per the brief's rule: "keep BUILDLOG.md honest: where AI helped, where it was wrong, what you changed."

## How this was built

The whole thing was built with Claude as the pair-programmer, working directly against this brief. Every requirement in Section 6 was treated as the literal spec; the phase structure in Section 8 was followed in order (design doc first, gated; hardened submission path second, gated; delivery/dashboard/proof third, gated).

## Where AI helped

- Turning the brief's three request-path architecture (owner/authenticated, customer-site/cached-public, visitor/protected-public) into an actual Express route layout — `src/routes/{auth,widgets,dashboard}.js` for the authenticated paths, `src/routes/public.js` for the CORS-open ones, kept in separate files specifically so "which requests are trusted" stays visually obvious file-by-file.
- The tenant-isolation pattern: one shared `loadOwnWidget(id, customerId)` helper (`src/lib/tenant.js`) used by every route that touches a widget or its submissions, so "does this belong to this customer" is answered in exactly one place instead of being re-derived per route and potentially getting it wrong somewhere.
- The enrichment fallback chain and the safe-side-effect pattern (`src/lib/geo.js`, `src/lib/email.js`) — provider A, then B, then degrade to nulls, and a side effect that's caught but never rethrown.
- Writing `public/widget.js` as a dependency-free vanilla script (no bundler, no framework) since it has to run unmodified on an arbitrary third-party page.

## Where it was wrong, and what I changed

- **Real bug, caught during evidence-gathering, not code review.** Probe 2 ("malformed and oversized payloads -> clean 4xx JSON errors, never a 500") initially failed for one case: sending a request body that isn't valid JSON at all (`not json{{{`) returned a raw `500 Internal server error`, not a 4xx. `express.json()` throws a `SyntaxError` when it can't parse the body, and that error was falling straight through to the app's generic error handler, which just logs and returns 500 for everything. Fixed in `src/server.js`'s error middleware: it now checks for `err.type === "entity.parse.failed"` (the marker Express's body-parser sets) and returns a clean `400 {"error":"Malformed JSON body."}` instead. Re-ran the probe afterward and captured the corrected transcript in `EVIDENCE.md` — the before/after is left in there rather than quietly reworded, since the brief explicitly said this is what AI-assisted-but-honest means in practice.
- **The embed snippet initially didn't match the widget script it was pointing at.** The first version of `embedSnippet()` (in `src/routes/widgets.js`) generated `<script src=".../widget.js?id={id}">`, but `public/widget.js` was written to read the widget id from a `data-widget-id` attribute on its own `<script>` tag (via `document.currentScript`), not from a query string — a mismatch that would have meant every embed snippet the API ever handed out was silently broken. Caught while wiring up the second-origin test page for Phase 3, before any real customer would have hit it. Fixed the generator to emit `<script src=".../widget/v1/widget.js" data-widget-id="{id}" async>`; `DESIGN.md` and `EVIDENCE.md` reflect the corrected shape.
- **Router-wide auth middleware swallowed unrelated 404s.** `src/routes/dashboard.js` originally did `router.use(requireAuth)` and was mounted at the app root (`app.use(dashboardRoutes)`, no path prefix, since the router itself owns two different prefixes — `/widgets/:id/...` and `/dashboard/...`). A path-less `router.use()` runs for *every* request that reaches that router, whether or not any route inside it actually matches the URL — so a request to a completely unrelated, nonexistent path (e.g. `GET /nonexistent`) was being rejected with `401 Missing or malformed Authorization header` by this router before it ever got the chance to fall through to the app's real 404 handler, silently telling an unauthenticated caller "this needs a token" about a route that doesn't exist at all. Caught the same way as the JSON-parse bug: by deliberately probing an edge case (an unmatched path) while doing the final verification pass, not by reading the code and spotting it. Fixed by moving `requireAuth` from `router.use()` to an explicit per-route middleware on each of the three routes — Express only runs a route-specific middleware once it has already matched the path, so an unmatched path now correctly falls through to `/widgets` (auth-protected there too) and finally to the app's 404 handler instead of being intercepted early.
- **Geo mock IPs.** Loopback (`127.0.0.1` / `::1`) has no real geolocation, which would make the fallback chain untestable when curling from the same machine the server runs on — every request would short-circuit to "no IP to enrich" before ever reaching provider logic. Substituted a fixed RFC 5737 TEST-NET-1 documentation address (`192.0.2.1`, never a real address) for loopback specifically so the enrichment chain has something to do during local testing; this is called out in a code comment in `src/routes/public.js` (`clientIp()`), not left implicit.

## What I'd explain if asked about any 2-3 lines

- `src/middleware/rateLimit.js`'s hand-rolled `widgetLimiter`: `express-rate-limit` keys by IP out of the box, but a flood aimed at one widget can come from many different IPs (the realistic abuse pattern for a public embed), so per-widget limiting needed its own counter — a `Map<widgetId, timestamp[]>` filtered to a sliding 60s window on every check. It also means any request naming a widget counts against that widget's budget even if it's later rejected for other reasons (oversized, malformed) — intentional, so an attacker can't dodge the limiter by sending garbage that still names a real widget.
- `src/lib/tenant.js`'s `loadOwnWidget` returns `null` for both "no such widget" and "exists but isn't yours," and every route that uses it returns a flat `404` either way — never `403` — so a rejected request never confirms to the caller that a given widget id exists at all for some other tenant.
